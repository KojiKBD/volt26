# Simply Love Functional Inventory for VOLT26

## Purpose

This living document tracks non-visual Simply Love behavior that may need to be retained, adapted, replaced, or omitted as VOLT26 becomes a standalone ITGmania theme. It deliberately excludes purely decorative assets and styling. Mixed features are included when their source combines behavior and presentation.

## Status and decision vocabulary

**Decision**

- `Assess`: investigation or project-owner decision is still required.
- `Adopt`: retain the behavior with minimal semantic change.
- `Adapt`: retain the behavior but integrate it into VOLT26 architecture or UX.
- `Replace`: implement the same user need differently.
- `Omit`: intentionally exclude it and document the rationale.

**Implementation status**

- `Not started`
- `In progress`
- `Implemented`
- `Verified`

## Inventory entry requirements

Before an item is considered complete, record:

- the upstream Simply Love tag or commit reviewed;
- behavioral responsibility and user-visible result;
- source landmarks and important dependencies;
- persisted preferences or profile data;
- the VOLT26 decision and rationale;
- the implementation branch and VOLT26 destination;
- automated checks, manual verification steps, and result.

## Core runtime assessment

### CORE-01 — Theme initialization and shared runtime state

- **Behavioral responsibility:** creates the global `SL` namespace, per-player state, per-game-cycle state, timing/scoring/life constants, EX weights, GrooveStats service state, request/download caches, and reset behavior. `InitializeSimplyLove()` resets both players and the game-cycle globals at script load and again when the title menu is entered.
- **Important dependencies:** `ThemePrefs`; `PREFSMAN`; `Branch.GameplayScreen()`; `CreateGrooveStatsPlayerOptionKeys()` from the GrooveStats helper; `LoadUnlocksCache()` from the GrooveStats helper; engine globals and enum helpers. Script load order is therefore part of the contract.
- **State boundaries:** player option selections, parsed chart caches, evaluation pane choices, API-session data, favorites, stage statistics, active rate, stage/continue counters, screen-return targets, timers, screenshot texture, and session timing are held in memory. Theme preferences and the GrooveStats unlock cache are read from persistent storage by dependencies; `SL_Init.lua` does not save them directly.
- **VOLT26 delta:** on `codex/standalone-core-foundation`, `VOLT26` is now the authoritative namespace with `Meta`, `State`, `Core`, and `ThemePrefs` interfaces. `VOLT26.Preferences` temporarily retains the inherited game-mode scoring data required by compatibility consumers, while `SL` and `InitializeSimplyLove` remain temporary aliases for screens that have not yet migrated. The broad inherited state shape still requires domain separation.
- **Mixed responsibilities:** visual color tables live beside scoring constants, online state, navigation state, and player/session data. These responsibilities should be separated during the standalone foundation work even if compatibility aliases are temporarily retained.
- **Recommended decision:** `Adapt` — retain reset semantics and the state required by accepted features, move it behind VOLT26-owned runtime modules, and remove state belonging to omitted features.
- **Verification pending:** start the theme, return to the title menu after a completed game cycle, and confirm that transient player/session/stage state resets while persistent theme/profile settings remain intact; repeat for one and two players.

### CORE-02 — Compatibility validation and startup failure handling

- **Behavioral responsibility:** parses the engine version, accepts only ITGmania `1.3.0` or newer, accepts the `dance`, `pump`, `techno`, `para`, and `kb7` game types, and redirects unsupported configurations to `ScreenSystemOptions` with a localized system message. It also prevents the Thonk visual style from running under the Windows D3D render path that lacks render-to-texture support.
- **Important dependencies:** `ProductFamily()`, `ProductVersion()`, `GAMESTATE`, `HOOKS`, `PREFSMAN`, `SCREENMAN`, localized `ScreenInit`/theme-option strings, the `SM()` system-message utility, and `ScreenSystemOptions`/`ScreenThemeOptions` metrics.
- **State and persistence:** no direct persistence. The result depends on engine preferences such as the active game and video renderer.
- **VOLT26 delta:** on `codex/standalone-core-foundation`, `ScreenInit` is a direct VOLT26 screen, retained engine/game validation uses VOLT26 wording, and the Thonk-only renderer guard is omitted. `SL-SupportHelpers.lua` remains an inherited implementation dependency pending CORE-05 migration. `_G.Volt26InitHandoff` remains a transient presentation handoff rather than compatibility state.
- **Mixed responsibilities:** the Thonk render-to-texture guard is visual-style-specific and should not move into standalone VOLT26 unless VOLT26 adopts a feature with the same renderer requirement. Theme-version and author readers in `SL-SupportHelpers.lua` are metadata helpers, not compatibility checks.
- **Recommended decision:** `Adapt` — retain the early engine/game guard, replace Simply Love wording and supported-version policy with a VOLT26-owned compatibility contract, and omit the Thonk-only branch unless independently required.
- **Verification pending:** boot on the minimum supported ITGmania version and one newer version; simulate an older version and unsupported game; confirm one actionable message and a safe redirect without a Lua error.

### CORE-03 — Theme preferences

- **Behavioral responsibility:** defines theme-wide defaults and option-row values, initializes fallback `ThemePrefs`/`ThemePrefsRows`, validates saved values by type and allowed-value membership, removes unknown keys, and saves the current theme section to `Save/ThemePrefs.ini`.
- **Important dependencies:** fallback-theme `ThemePrefs.InitAll()`, `ThemePrefsRows`, `IniFile`, date functions, localized strings, `range()`, `map()`, and `FindInTable()` from `06 SL-Utilities.lua`.
- **Persistent data:** navigation toggles; game/style/sort defaults; menu timers; color and visual-style choices; sampling, banner, keyboard, scoring, tournament, GrooveStats, unlock, QR-login, and lobby settings; edit-mode history; event state. VOLT26 adds `VOLT26MementosDashHighScore` and the `VOLT26` visual-style choice.
- **VOLT26 delta:** on `codex/standalone-core-foundation`, the theme identity owns a separate preference section, `VOLT26Color` is introduced, and Visual Style selection is removed from operator-facing theme options. A fixed `VisualStyle=VOLT26` compatibility value and `SL_CustomPrefs` registry remain temporarily for unmigrated screens; legacy preference migration is not yet implemented.
- **Mixed responsibilities:** a single registry couples core navigation and timing preferences to visual styles, optional online services, tournament behavior, an event unlock, and a minigame score. `VisualStyle` becomes obsolete when VOLT26 is no longer a Simply Love visual style.
- **Recommended decision:** `Adapt` — create a VOLT26-owned preference registry, preserve accepted keys with an explicit migration/default policy, split optional-feature preferences by domain, and retire `VisualStyle` checks from runtime branching.
- **Verification pending:** load valid legacy values, invalid types, invalid enum values, and unknown keys; restart ITGmania; verify accepted values persist under the VOLT26 section and invalid/retired values migrate or reset as documented.

### CORE-04 — Screen branching and navigation decisions

- **Behavioral responsibility:** selects profile/login/color/style/play-mode screens; applies game-mode preferences and reloads metrics; routes music/course selection, options, gameplay, evaluation, profile save, name entry, continues, game over, and title return; reconciles stage cost with music rate; and checks available credits for continues.
- **Important dependencies:** `ThemePrefs`, `SL.Global`, `GAMESTATE`, `PREFSMAN`, `PROFILEMAN`, `STATSMAN`, `SCREENMAN`, `THEME`, `MESSAGEMAN`, `GetCredits()`, `SetGameModePreferences()`, and fallback `Branch.AfterInit()`, `Branch.TitleMenu()`, and `Branch.GameplayScreen()` functions. Corresponding `metrics.ini` `PrevScreen`/`NextScreen` values form part of the route graph.
- **State and persistence:** mutates joined players/current style, `SL.Global.GameMode`, stage and continue counters, and player-option return targets. It reads persistent theme and engine preferences but does not save them.
- **VOLT26 delta:** on `codex/standalone-core-foundation`, `VOLT26.Navigation` owns the first public route helper, the ruleset is forced directly to ITG without a Visual Style condition, and the title choices are direct VOLT26 metrics. The remaining branch graph and compatibility `SelectMusicOrCourse` global are still inherited.
- **Mixed responsibilities:** optional-screen UX, coin-op policy, online login, stage accounting, profile persistence, gameplay mode selection, and end-of-session policy are combined in one module. Stage accounting belongs with session/gameplay behavior even though it currently controls navigation.
- **Recommended decision:** `Adapt` — define a VOLT26 route graph and explicit supported modes, retain only accepted coin/profile/session policies, and replace the temporary `VisualStyle` condition with standalone defaults.
- **Verification pending:** exercise the complete startup-to-title-to-profile-to-music-to-options-to-gameplay-to-evaluation route for one and two players, plus course, event, cancel, fail, continue, name-entry, and game-over branches.

### CORE-05 — Shared helpers, text, UTF-8, and support utilities

- **Behavioral responsibility:** provides generic table/system-message helpers (`TableToString`, `SM`, `range`, `map`, `deduplicate`, and lookup/string conversion), UTF-8 string primitives, emoji diffusion, multilingual wrapping/truncation, engine/metadata support helpers, and a large inherited `SL-Helpers.lua` collection.
- **Important dependencies:** Lua string/table APIs; StepMania actor types and global managers; fallback utility functions; `SL`, `ThemePrefs`, `Branch`, and theme asset/metric lookup. `SL-Helpers-Text.lua` monkey-patches `BitmapText`, so its load order and global effect are part of the contract.
- **State and persistence:** generic utilities are stateless. Several functions in `SL-Helpers.lua` read or mutate engine preferences and runtime player state; `ResetPreferencesToStockSM5()` is state-changing and must not be treated as a harmless formatting helper.
- **VOLT26 delta:** `SL-Helpers.lua` and `SL-SupportHelpers.lua` are source-identical to upstream. Utility, text, and UTF-8 files are source-equivalent apart from line-ending differences.
- **Mixed responsibilities and inventory routing:** timing-window and worst-judgment helpers belong with `GAME-02`; EX counts and score calculation with `GAME-01`/`GAME-03`; game-mode preference application and stock-reset behavior with `CORE-03`; notefield geometry and asset lookup with implementation/presentation; course duration and stage helpers with `GAME-05`/session behavior. CORE-05 should retain only genuinely cross-cutting primitives.
- **Recommended decision:** `Adapt` — keep proven UTF-8/text behavior where needed, replace broad globals with namespaced VOLT26 helpers, and assign domain-specific functions to their owning inventory items before pruning.
- **Verification pending:** run Lua syntax/loading checks in the target engine; cover UTF-8 length/substrings, emoji attributes, Japanese wrapping, truncation, ranges in both directions, table lookup/deduplication, and system-message formatting.

## Profiles and options assessment

### PROFILE-01 — Player profile discovery, selection, and profile-derived state

- **Behavioral responsibility:** enumerates local profiles and their display metadata, reads recent theme modifiers for profile previews, discovers profile avatars, and coordinates guest, local-profile, and memory-card selection. The profile screen also handles joining and unjoining, coin consumption and refunds, duplicate-profile prevention for two players, default-profile selection, and the fast profile switch used from music selection.
- **Load and save contract:** the engine calls `VOLT26.Profile.LoadCustom` and `VOLT26.Profile.SaveCustom` through the `[Profile]` metrics; the inherited global names remain compatibility adapters. Loading resets player options and transient player state while preserving the current session's stage history, validates stored keys by datatype and valid option-row values, restores engine modifiers, resets disabled timing windows, and reapplies the operator-defined fail type. Saving writes the permitted custom modifiers and the engine `PlayerOptionsString`.
- **Important dependencies:** `PROFILEMAN`, `GAMESTATE`, `MEMCARDMAN`, `FILEMAN`, `PREFSMAN`, `IniFile`, `ActorUtil`, `ThemePrefs`, `CustomOptionRow()`, `GetDefaultFailType()`, `SL[pn]`, profile-screen engine index conventions, corresponding `metrics.ini` routes, and the GrooveStats and ITL read/write helpers.
- **Persistent data:** each persistent profile receives `<theme display name> UserPrefs.ini`, with a section also named from the theme display name. GrooveStats and ITL data are read and written as side effects of the same lifecycle. Engine-level default local-profile IDs and coin preferences also affect selection behavior. Guest state is transient, although stage history is deliberately retained across an in-session profile switch.
- **VOLT26 delta:** on `codex/standalone-profile-flow`, `VOLT26.Profile` owns the engine persistence callbacks, guest loading, avatar lookup, preferred-style access, and fast-switch state exposed to SCREEN code. ScreenSelectProfile no longer reads `SL.Global` or branches to SRPG presentation. Profile storage now derives its filename and section from the standalone VOLT26 theme identity.
- **Mixed responsibilities:** profile persistence is coupled to online-service and tournament files; profile selection is coupled to arcade credit policy, player joining, visual previews, and music-screen fast switching. These need explicit boundaries even if the existing screen behavior is retained initially.
- **Recommended decision:** `Adapt` — retain local, guest, and memory-card profile support plus validated per-profile modifiers, move persistence to an explicit VOLT26 schema with a documented Simply Love migration path, and make GrooveStats/ITL hooks optional integrations rather than mandatory profile side effects.
- **Verification status:** on `codex/standalone-profile-flow`, direct hidden startup of `ScreenSelectProfile` succeeds without Lua or asset-loading errors for one and two joined players. The project owner manually verified guest selection, two-player selection, local-profile selection, and cancellation. Memory-card profiles, duplicate selection, late join, fast switching, coin consumption/refund, and persistence validation across restart remain extended-coverage cases.

### OPTIONS-01 — Player option construction and persistence

- **Behavioral responsibility:** builds custom option rows for speed, noteskin and variant, judgments, combo and hold graphics, notefield placement, music rate, chart selection, visibility, life display, score targets, timing feedback, gameplay statistics, and edit/attack modifiers. It translates selections between localized choices, `SL[pn].ActiveModifiers`, and the engine's preferred or stage `PlayerOptions`, then chooses the next options, music, or gameplay screen.
- **Application contract:** `CustomOptionRow()` exposes Lua option-row definitions to `metrics.ini`; generic load/save behavior is overridden where an option must mutate engine state or broadcast a preview/update message. `ApplyMods()` replays all rows after profile loading and on late join so saved settings apply even when the player never opens the options screen.
- **Important dependencies:** `SL[pn].ActiveModifiers`, `SL.Global.ScreenAfter`, `GAMESTATE`, `SCREENMAN`, `NOTESKIN`, `ThemePrefs`, `MESSAGEMAN`, chart/course APIs, gameplay-layout helpers, GrooveStats availability, localized strings, the three `ScreenPlayerOptions` metric groups, preview actors, and `PROFILE-01` for persistence.
- **State and persistence:** option changes update engine preferred/stage modifiers and in-memory theme state. Per-profile persistence is performed later by `SaveProfileCustom()`; music rate, current steps/trail, evaluation-pane defaults, and next-screen targets also mutate shared game-cycle state.
- **VOLT26 delta:** `SL-PlayerOptions.lua` is source-identical to the reviewed upstream baseline. VOLT26 assets are discovered through existing noteskin, judgment, hold-judgment, and combo-font enumeration, but the behavior remains owned by Simply Love names, shared state, metrics, and screen actors.
- **Mixed responsibilities and inventory routing:** the option framework currently embeds policy for tournament restrictions, online scoreboxes, chart selection, gameplay scoring displays, timing windows, course behavior, and screen navigation. The underlying feature decisions belong to their respective `GAME-*`, `ONLINE-01`, `EVENT-02`, `SELECT-*`, and `CORE-04` inventory items rather than being decided implicitly by the options UI.
- **Recommended decision:** `Adapt` — retain the proven per-player option lifecycle and profile application behavior, define a VOLT26-owned option registry, and include rows only for features accepted elsewhere in the inventory. Replace screen-specific actor manipulation with explicit update messages or interfaces where practical.
- **Verification pending:** load saved options without visiting the screen, change every retained row on all three pages, test localized values and unavailable assets, confirm live previews and engine modifiers, and repeat for one player, two players, routine, course, edit, late-join, and restart scenarios.

### OPTIONS-02 — Operator/service options and active option-row behavior

- **Behavioral responsibility:** defines the service-menu hierarchy and helper rows for theme selection, editor noteskin, default fail type, long/marathon thresholds, wheel speed, video renderer, global and visual offsets, memory cards, and custom-song limits. The service overlay supplies contextual help, remembers the active row when returning from child screens, saves theme preferences, rebuilds localized preference rows, and revalidates engine/game compatibility when leaving.
- **Important dependencies:** `PREFSMAN`, `ThemePrefs`, `ThemePrefsRows`, `SL_CustomPrefs`, `SL.Global.PrevScreenOptionsServiceRow`, `SCREENMAN`, `GAMESTATE`, `IniFile`, theme and engine metadata, compatibility helpers, localized strings, and the `ScreenOptionsService*` hierarchy in `metrics.ini`.
- **Persistent data:** engine preferences include default modifiers/fail type, editor noteskins, song-length thresholds, wheel speed, renderer order, timing offsets, memory-card behavior, and custom-song limits. Theme-owned rows persist through `ThemePrefs.Save()`. The remembered active option row is transient session state.
- **VOLT26 delta:** `SL-OperatorMenuOptions.lua` and the assessed service actors are source-equivalent to the upstream baseline. The inherited hierarchy still exposes Simply Love visual-style and optional-feature preferences; VOLT26 currently enters it as one selectable visual style rather than owning a curated operator menu.
- **Mixed responsibilities:** engine-wide configuration, VOLT26 preferences, optional online/tournament features, theme switching, compatibility validation, and service-menu presentation share one hierarchy. Theme switching and renderer changes also have wider installation or restart consequences than ordinary theme preferences.
- **Recommended decision:** `Adapt` — keep the engine settings that VOLT26 operators need, create a smaller VOLT26-owned service hierarchy, separate machine preferences from theme and optional-integration settings, and remove visual-style selection from the standalone runtime.
- **Verification pending:** enter every retained child screen, change and persist each custom row, return and confirm active-row restoration, restart where required for renderer/theme changes, and verify invalid compatibility choices redirect safely with an actionable message.

## Music selection assessment

### SELECT-01 — Music selection state and helper logic

- **Behavioral responsibility:** initializes the standard music screen for a new gameplay entry, restores the selected music rate, reapplies profile or guest modifiers after joins and profile changes, preserves the menu timer across auxiliary screens, and automatically changes style so single, double, and routine charts can coexist in the wheel. Shared helpers start and stop casual-mode samples, position wheel title text, and derive the stage label from continues, song cost, and session progress.
- **Important dependencies:** `SL.Global`, `SL[pn]`, `GAMESTATE`, `PROFILEMAN`, `SCREENMAN`, `PREFSMAN`, `ThemePrefs`, `SOUND`, `THEME`, `LoadGuest()`, `ApplyMods()`, `generateFavoritesForMusicWheel()`, the option/profile lifecycle, and the `ScreenSelectMusic` metrics and engine music wheel.
- **State and persistence:** mutates the preferred song music rate, current style, transient gameplay-reload flag, current player modifiers, and preserved menu time. It reads theme and engine preferences but delegates durable player settings to `PROFILE-01` and `OPTIONS-01`.
- **VOLT26 delta:** on `codex/standalone-music-selection`, `VOLT26.MusicSelection` owns screen preparation, active-rate access, guest/profile refresh, and modifier reapplication. `ScreenSelectMusic` now composes the VOLT26 background, layout, wheel type, row renderer, and hidden stock actors directly; production song-selection code no longer reads `VisualStyle`, and the componentized layout no longer reads the `SL` compatibility alias for music rate. Shared timer preservation, auto-style, favorites, sort, search, leaderboard, and input-test behavior remain inherited pending their respective decisions.
- **Recommended decision:** `Adapt` — retain the initialization and re-entry contracts, expose them through a VOLT26-owned music-selection controller, and replace the visual-style conditional with the standalone screen composition. Route stage accounting and player-option persistence through their owning modules rather than duplicating them here.
- **Verification status:** direct hidden loading reaches `ScreenSelectMusic`, loads `VOLT26MusicWheel`, the componentized VOLT26 layout, and the native VOLT26 song rows without errors from the migrated files. The project owner manually verified the normal profile-to-music route, wheel navigation, song and difficulty navigation, and return-to-title behavior for one and two players. Direct loading without the normal route still triggers the inherited sort-menu nil-style warning because ITGmania has no current style. Re-entry after evaluation/player options, profile switching, late join, memory-card reload, rate/modifier restoration, favorites, and courses remain extended coverage. The current Song Select presentation is intentionally accepted as work in progress and will be redesigned only after the standalone migration is complete.

### SELECT-02 — Song search, filtering, sorting, and wheel behavior

- **Behavioral responsibility:** drives the reusable Lua wheel, opens the sort/action overlay, changes engine sort order and preferred-song lists, switches regular/course play, game mode, and style, and routes to search, practice, profile switching, song reload, downloads, online lobbies, input testing, leaderboards, and evaluation summary. Search filters the current style's songs by title, transliterated title, pack, exact meter, and ten-BPM tier, then focuses the selected result and changes incompatible sort orders back to group sorting.
- **Important dependencies:** the engine `MusicWheel`, `SONGMAN`, `GAMESTATE`, `PROFILEMAN`, `SCREENMAN`, `MESSAGEMAN`, `PREFSMAN`, `ThemePrefs`, `SL.Global`, `SetGameModePreferences()`, profile playlist and favorites files, GrooveStats availability, localized prompt strings, and `Consensual-sick_wheel.lua` for the casual Lua wheels.
- **State and persistence:** mutates current sort, preferred-song source, play mode, game mode, style, current song/course, menu timer, and screen-routing flags. Profile switching explicitly saves player and machine profiles; the search query and candidate list are transient, while playlists and favorites are external profile files.
- **VOLT26 delta:** the search settings, search input, sort-menu behavior, and reusable wheel are semantically equivalent to the reviewed upstream baseline. WebSocket endpoints use plaintext `ws://`; response data and downloaded archives cross trust boundaries before affecting profile options, in-memory state, and the song directory.
- **Recommended decision:** `Adapt` — retain GrooveStats as an optional integration only after separating transport, credential storage, score validation, response schemas, and UI consumers behind VOLT26-owned interfaces. Require encrypted endpoints where supported, strict response and option validation, explicit connection/error states, safe archive extraction with bounded downloads, and independent enablement for login, lookup, submission, unlocks, and lobbies. Treat online lobbies as experimental until their synchronization and disconnect state machine is tested independently.
- **Verification pending:** run with services disabled, fully available, partially available, blocked, offline, malformed, slow, and disconnected mid-request; test missing/invalid API keys, QR login cancellation and reconnect, one/two players, pad versus keyboard/autoplay, every score-invalidating rule, hash mismatches, duplicate submissions, remote option payloads, cache expiry, course rejection, and evaluation exit during callbacks. For lobbies, cover host/join/search/leave, missing songs, late peers, screen divergence, gameplay ready-up, evaluation waits, reconnects, five-second disconnect, callback cleanup, and all supported player/style combinations. Security tests must include untrusted JSON, oversized responses/downloads, path traversal and zip-bomb archives, invalid content types, unsafe pack names, and credential/log redaction.

## Event and tournament assessment

### EVENT-01 — Event progress and evaluation interaction

- **Behavioral responsibility:** consumes RPG and ITL data returned by score submission, presents current score/point deltas, quest completion, unlocks, leaderboard entries, and per-event progress, and temporarily takes ownership of evaluation input so players can page through event result panes before returning to the normal evaluation flow. Compact progress summaries are also populated beside the standard evaluation result area.
- **Important dependencies:** successful `ONLINE-01` submission responses and their RPG/ITL schemas, GrooveStats date parsing, evaluation actor names and input callback arbitration from `EVAL-04`, current song/banner data, profile/player side mapping, optional SRPG10 globals and assets, widescreen/player-count layout rules, and event-specific strings, colors, and pane commands.
- **State and persistence:** the overlay and compact summaries are screen-local views of the current server response. Quest unlock downloads and ITL folder unlocks delegate persistence to `ONLINE-01` and `EVENT-02`; this actor does not independently store progress. Its input ownership is transient but can block normal evaluation navigation until explicitly released.
- **VOLT26 delta:** event behavior is source-equivalent to upstream and is tightly interwoven with SRPG10 presentation, GrooveStats response shapes, fixed evaluation actor names, and a mutually exclusive RPG-first rule when a chart belongs to more than one event. There is no event-provider interface or normalized progress model.
- **Recommended decision:** `Adapt` — retain event results only as an optional consumer of a validated online response. Define a provider-neutral VOLT26 event-result schema, support multiple simultaneous event memberships deterministically, keep presentation packages separate, and centralize evaluation input ownership so missing or malformed event data can never trap the screen.
- **Verification pending:** test no event, RPG only, ITL only, both events, unknown events, incomplete/malformed responses, empty/full leaderboards, rivals/self entries, positive/negative/zero deltas, long localized text, one/two players, 4:3/widescreen, missing assets/modules, repeated pane navigation, normal exit/cancel, and online timeout or evaluation transition while the event overlay owns input.

### EVENT-02 — Tournament mode and local ITL records

- **Behavioral responsibility:** tournament preferences force a selected EX/ITG scoring display, control step-stat visibility, keep the FA+ pane available, and optionally replace CMods with an MMod on charts marked `no cmod`. Independently, the ITL subsystem recognizes 2026 event songs, validates eligible 1.0x dance scores using GrooveStats rules plus mines and timing-window requirements, calculates clear types and event points, preserves the best result by chart hash, maps song paths to hashes, records unlocked folders, and exposes local ITL data to the wheel and evaluation.
- **Important dependencies:** `EnableTournamentMode`, `ScoringSystem`, `StepStats`, and `EnforceNoCmod` preferences; player-option construction; gameplay step-stat and versus actors; title/subtitle metadata; chart hashes and EX/judgment calculations; `ValidForGrooveStats()`; profile directories; JSON/file APIs; current ITL pack naming; evaluation lifecycle; and unlock folders returned through `ONLINE-01`.
- **State and persistence:** tournament configuration persists as theme preferences and changes the available player-option surface. Per-player `pathMap`, `hashMap`, and `unlockFolders` are loaded from and written to `ITL2026.json` in an explicit profile; guest play has no durable ITL record. Event activity is currently hard-coded to always true, and year/pack/file identifiers are embedded in the implementation.
- **VOLT26 delta:** the assessed implementation is source-equivalent to upstream. Tournament policy is distributed across preferences, player options, gameplay, and evaluation. The ITL implementation couples a specific annual event format to global functions and contains a best-score update path whose strict-improvement comparison occurs after assigning the new EX value, preventing that branch from being true and risking stale judgment details on an improved score.
- **Recommended decision:** `Adapt` — retain a small, explicitly specified tournament-policy layer and make event scoring a versioned provider module rather than permanent core behavior. Define enforcement versus display settings separately, avoid silently changing speed mods without feedback, move annual identifiers and active dates into validated event configuration, use an atomic/versioned profile schema, and fix best-score comparison before any adoption.
- **Verification pending:** test every tournament preference combination, option visibility and forced scoring, `no cmod` detection through display/transliterated titles, C/M/X mods, one/two players, courses, edit mode, and restoration after leaving tournament mode. For ITL, use fixtures for eligibility, points and rounding, every clear type, ties and strict improvements, resynced/path-mapped charts, malformed chart metadata and JSON, missing/guest/read-only profiles, renamed/moved songs, unlock folders, year rollover, event inactive state, and concurrent two-player writes.

## Removable-media content assessment

### CONTENT-01 — Custom songs from USB profiles

- **Behavioral responsibility:** exposes ITGmania engine preferences for enabling memory cards and profile-hosted custom songs, maximum song count, load timeout, duration, and size. The theme hides the USB options when the engine does not provide `CustomSongsEnable`; actual discovery, validation, loading, limits, and cleanup of removable-media songs are engine responsibilities.
- **Important dependencies:** ITGmania memory-card/static-mount configuration, `PREFSMAN` support for `MemoryCards`, `CustomSongsEnable`, `CustomSongsMaxCount`, `CustomSongsLoadTimeout`, `CustomSongsMaxSeconds`, and `CustomSongsMaxMegabytes`, the service-option framework from `OPTIONS-02`, profile selection/reload behavior from `PROFILE-01`, and operating-system mount permissions. The current guide still points to old StepMania 5.1-era setup material and names Simply Love.
- **State and persistence:** all settings are engine preferences and survive restart through ITGmania. Song files remain on the removable profile media and are not copied by this theme code. The option rows accept existing custom timeout values, while duration/size rows fall back to their first listed value if an existing preference is outside their predefined choices.
- **VOLT26 delta:** the option behavior is source-equivalent to upstream, but the documentation and compatibility comments target legacy StepMania/Simply Love. Capability detection checks only one preference, and the UI does not communicate mount, scan, timeout, limit, or partial-load failures beyond engine behavior.
- **Recommended decision:** `Adapt` — retain the operator controls when supported by the declared ITGmania baseline, relabel and rewrite the workflow for VOLT26, preserve all valid existing values, and surface engine capability and load failures clearly. Keep removable-media mounting and song sandboxing as documented engine/operator prerequisites rather than theme-owned filesystem logic.
- **Verification pending:** test a clean supported ITGmania install with the feature absent/present; memory cards off/on; valid, missing, read-only, slow, removed-mid-scan, and multiply mounted media; zero/one/many songs; duplicate songs; malformed simfiles; nested and non-ASCII paths; each count/time/size boundary; timeout and partial-load behavior; profile reload, late join, restart persistence, and safe removal without stale wheel entries or crashes.

## Service and maintenance assessment

### SERVICE-01 — Input diagnostics and pad testing

- **Behavioral responsibility:** provides a service screen that displays attached devices, mapped game inputs, and currently held unmapped device inputs; draws dance, pump, techno, and dance-solo pad highlights; falls back to the engine input list for other games; and reuses the same pad actor in Event Mode music selection and evaluation diagnostics. Double and routine modes match events by controller rather than player number.
- **Important dependencies:** raw input callbacks, `Def.DeviceList`/`Def.InputList`, game/style/controller enums, `TestInputEvent` broadcasts, dedicated-menu-button and `AllowDanceSolo` preferences, localized labels, screen metrics, and input-routing coordination with `SELECT-02` and `EVAL-04`.
- **State and persistence:** held unmapped inputs and highlight visibility are screen-local and are not persisted. Input mappings are engine-owned and read-only here. Callback registration is explicit on the service screen and through parent overlay handlers elsewhere.
- **VOLT26 delta:** diagnostic behavior and pad mappings are source-equivalent to upstream. Behavioral mapping is embedded in presentation coordinates/assets; custom handling is limited to dance, pump, and techno, while para/kb7 fall back to a different information model. Release detection hides a highlight on the first release even if multiple physical inputs map to the same logical panel.
- **Recommended decision:** `Adapt` — retain diagnostics as a shared VOLT26 input-state model with separate renderers per game, reference-count held physical inputs per logical button, and define callback ownership/cleanup consistently across service, selection, and evaluation screens. Preserve the engine fallback for unsupported games and show controller/player mapping explicitly.
- **Verification pending:** test every supported game/style, one/two players, single/versus/double/routine/solo, dedicated and gameplay menu buttons, keyboard/joystick/multiple devices, mapped/unmapped inputs, simultaneous bindings to one panel, repeats/releases/disconnects, late join, opening and closing diagnostics from every host screen, and callback/input-redirection cleanup.

### SERVICE-02 — Event-download status and navigation

- **Behavioral responsibility:** snapshots the transient `SL.Downloads` registry on entry, presents up to six scrollable items with progress, byte counts, completion and errors, refreshes every 0.1 seconds while work remains, and returns to music/course selection on Start, Back, or Select. The screen is reachable from music selection only when GrooveStats is connected and automatic unlock downloads are enabled.
- **Important dependencies:** download records and HTTP callbacks created by `ONLINE-01`, `Consensual-sick_wheel.lua`, named candidate actors, input callbacks, localized status strings, song/course branching, and the assumption that the download table's size remains constant while the screen is open.
- **State and persistence:** the viewer writes no durable state. It reads transient request objects and byte/error fields; successful extraction and the durable unlock cache belong to `ONLINE-01`. Completed entries remain in memory for the game cycle, and the candidate list does not incorporate downloads added after screen entry.
- **VOLT26 delta:** the viewer is source-equivalent to upstream and combines a fixed-size snapshot with polling and presentation-specific actor contracts. It cannot cancel or retry, distinguish download from extraction/reload phases, safely handle registry mutation, or trigger a song reload after successful installation.
- **Recommended decision:** `Adapt` if event downloads are retained; otherwise `Omit` with `ONLINE-01` unlock downloads. Model immutable download jobs with explicit queued/downloading/verifying/extracting/completed/failed/cancelled states, update the list through messages rather than polling, support safe retry/cancel, and expose whether newly installed content requires a controlled song reload.
- **Verification pending:** test zero/one/more-than-six jobs, jobs added or removed while open, unknown and zero totals, slow progress, completion during navigation, network/HTTP/content-type/unzip/write errors, duplicate names, long/non-ASCII labels, cancel/retry, leaving with active jobs, return to song/course selection, registry cleanup, and post-install song reload behavior.

## Session accounting assessment

### SESSION-01 — Gameplay duration and game-over statistics

- **Behavioral responsibility:** timestamps each player's gameplay actor on entry and stores elapsed screen time into the current per-stage snapshot on exit. Game Over sums available stage durations, counts played stages and non-miss per-column tap judgments, and shows session totals. Persistent profiles additionally show display name, lifetime songs played, avatar, and calories burned today unless the profile is configured to ignore engine calorie estimates.
- **Important dependencies:** per-stage storage from `EVAL-01`, per-column judgments from `GAME-02`, player-specific gameplay actor lifecycle, `GetTimeSinceStart()`, profile statistics and avatars, localized duration labels, late-join gaps, and the `ScreenGameOver` branch. The elapsed value measures time in the gameplay screen, not chart/music time.
- **State and persistence:** per-stage duration and derived session counts are transient in `SL[pn].Stages.Stats`; lifetime songs, profile name, calorie totals, avatar selection, and the ignore-calories flag are profile-owned persistent data. No separate session history is written by these actors.
- **VOLT26 delta:** on `codex/standalone-gameplay-evaluation`, gameplay duration writes through `VOLT26.Gameplay.StoreDuration()` into the controller-owned current-stage record. Timing still starts in `OnCommand` and writes only in `OffCommand`, and the inherited Game Over consumer still reads the compatibility state shape; pause/resume and abort semantics remain unresolved.
- **Recommended decision:** `Adapt` — retain lightweight game-cycle summaries, but define explicit session/stage records with monotonic start, pause/resume, completion, and abort semantics; derive tap totals from named normalized judgments; and label screen time versus active chart time accurately. Keep profile-owned lifetime and health-related data visually and semantically distinct from transient session totals.
- **Verification pending:** test normal completion, fail, give-up, Back/Escape, restart, pause, sync prompt, replay/practice, course transitions, screen reload, abnormal exit, late join/unjoin, one/two players, routine/shared-side play, empty and multi-hour sessions, missing/sparse stage records, holds/mines/checkpoints, profile/guest/memory-card players, ignored calories, restart persistence, and agreement with an independent monotonic timer and normalized judgment fixtures.
